Learn Rust by building Learning Lord

Audience: an experienced software engineer with five years of Clojure/ClojureScript and working Java/JavaScript knowledge, starting Rust from zero. Destination: a local playable town sandbox with a Rust server, Rust/Wasm frontend, and shared browser control.

This course is self-paced. A unit is one independently reviewable behavior, not a fixed-length session. Larger units may take several sessions. Complete the units in order; each module depends on the preceding module. Networking and browser concerns arrive after you can explain and test the simulation independently.

How to use the lessons

  1. Read the unit’s linked material, focusing on the named topic. The links are references, not a requirement to finish a whole book before writing code.
  2. Implement the exercise yourself. This document supplies requirements and acceptance criteria, not code, algorithms, hints, or solutions. Official documentation may contain its own generic examples.
  3. Demonstrate each acceptance criterion. For domain behavior, retain automated tests that check observable rules and invariants; for browser behavior, retain a short repeatable manual check where appropriate.
  4. Run formatting, Clippy, and relevant tests using the tooling commands. Fix unexplained warnings and failures.
  5. Answer the module’s reflection question in your own words. Record the completed unit number, relevant design decisions, and the next unit in your preferred notes. Commit the completed unit.

If you ask for help, supply the unit number, your current code, the compiler error or observed behavior, and what you expected. Review or explanations can stay focused on your implementation. Hints and worked solutions are provided only if you ask for them.

The rules define behavior. The curriculum defines its order of introduction. Earlier milestones deliberately exercise subsets: missing systems can be represented by explicit starter fixtures, but each later checkpoint must use the real preceding systems.

Where your existing experience helps

Clojure values and persistent collectionsRust bindings are immutable by default, but its standard collections are not persistent collections. Ownership and mutation permission are separate concerns. Module 1.
Keywords, maps, nil, and specsCompile-time structs and enums, exhaustive matching, and Option/Result make different guarantees. Module 2.
Sequences, map/filter/reduceIterators, laziness, consumption, and closures that capture owned or borrowed values. Module 3.

Use the Rust Book for concepts, standard library documentation for APIs, and the Cargo Book for project tooling. Crate reference links below follow their current documentation; use documentation matching the version you add to Cargo.lock.

0 · Own your toolchain

The scaffolding is supplied. Your work here is to understand and verify it.

0.1 · Run the starter

Read
Cargo basics; local setup and commands.
Work
Run the starter, inspect its manifest, and run the formatting, lint, and test commands.
Done when
You can identify source versus generated output, explain Cargo.lock and the toolchain pin, and reproduce a clean check. The initial test suite has zero tests; that is not evidence of game correctness.

0.2 · Use compiler feedback in Neovim

Read
rust-analyzer; rustc error explanations.
Work
Open the starter in Neovim. Make a temporary type error, inspect the diagnostic, read its explanation, and restore the program.
Done when
Hover, go-to-definition, diagnostics, and formatting work. You can get the same compiler failure from the terminal without relying on your editor.

Checkpoint: tooling is usable. Reflect: which feedback comes from Cargo, rustc, Clippy, and rust-analyzer?

1 · Values, ownership, and borrowing

1.1 · Describe one household

Read
Common programming concepts; formatting.
Work
Replace the setup message with a textual description of one household: its name, member count, money, and food. Compute its food requirement for a chosen number of days.
Done when
Changing the inputs changes the report correctly, including zero days. Explain the numeric types and expression results you chose.

1.2 · Own and inspect names

Read
Ownership; references and borrowing; slices.
Work
Add household renaming and a reusable report operation. Use the name again after producing a report.
Done when
You can explain every move and borrow involved, distinguish String from str, and account for any explicit copying. Rename and report work repeatedly, including a non-ASCII household name.

1.3 · Give the household structure

Read
Structs and methods; writing tests.
Work
Represent the household as a domain value and add tests for its report inputs and food requirement. Keep domain behavior usable without terminal output.
Done when
Two independent households can be inspected and changed without affecting each other. Tests cover the zero-day boundary and ordinary consumption requirements.

Checkpoint: inspect and rename a household. Reflect: how does a Rust move differ from rebinding a Clojure value or copying a Java reference?

2 · Model a settlement

2.1 · Families and their members

Read
Enums, Option, and match; vectors; hash maps.
Work
Represent multiple families, their members and starting skills, family inventories, and building ownership. Add and inspect an invited family.
Done when
Members belong to exactly one family, missing lookups are handled, and an invitation preserves all existing families. New families bring supplies but do not receive land automatically.

2.2 · Assign land

Read
Result and error propagation; Option reference.
Work
Represent the tile map and public/family zones. Let the player assign available land to a family.
Done when
Valid assignments succeed; out-of-bounds tiles, duplicate ownership, and nonexistent families fail without changing the world. Unassigned/public land remains distinguishable from family land.

2.3 · Define valid stock and payments

Read
Integer arithmetic APIs; test organization.
Work
Add domain operations for adding/removing stock and transferring money. Decide and record money units and quantity limits.
Done when
Insufficient funds or stock and numeric overflow fail without partial changes. A successful payment conserves the total money across both parties; a same-party payment cannot create money.

2.4 · Assemble the starter town

Read
Packages, crates, and modules; starter rules.
Work
Create the specified fixed starter settlement and a terminal inspection entry point. Record exact starting quantities. Separate reusable domain behavior from the executable.
Done when
The report includes land, people, buildings, stocks, and treasury. The fixture is valid and repeatable. Its initial buildings have valid ownership and nonoverlapping footprints.

Checkpoint: invite and allocate land in a headless town. Reflect: what can your types rule out, and what still requires runtime validation?

3 · Advance simulation time

3.1 · Advance a tick and a calendar

Read
Iterators; closures.
Work
Advance the world by a requested number of ticks and report day and season transitions. Use the starter calendar.
Done when
Zero ticks leave state unchanged. Day/season boundaries occur exactly once. Advancing in several batches matches advancing the same total number of ticks at once.

3.2 · Pause and change speed

Read
Time APIs; match control flow.
Work
Add a terminal driver supporting pause and the agreed speeds. Provide a way to advance exact ticks for tests.
Done when
Pause stops simulation time. Running at different speeds produces the same state after the same ticks and commands. A long pause does not produce a burst of catch-up ticks when resumed.

3.3 · Make runs inspectable

Read
Debug; running selected tests.
Work
Provide a repeatable scenario that accepts player actions at specified ticks and reports meaningful changes. Extend it as systems arrive.
Done when
Two fresh runs with the same initial conditions and actions agree. The output exposes enough state to explain a failed test without manually reading the whole world.

Checkpoint: run, pause, and inspect a season. Reflect: which behavior belongs to simulation time, and which belongs to real time?

4 · Move through the world

4.1 · Find a reachable work location

Read
Adding a dependency; pathfinding crate API.
Work
Add route queries over the map’s walkable tiles, including access to building interaction locations. Use an established pathfinding library.
Done when
Routes respect map bounds and obstacles. Already-at-destination, unreachable destination, and a blocked building entrance have explicit outcomes. Tests need not insist on one particular equally valid route.

4.2 · Walk over multiple ticks

Read
Patterns and matching; collection APIs.
Work
Give members destinations and advance movement over time. Handle an obstacle appearing while a member is traveling.
Done when
Members travel only through adjacent permitted tiles, stop on arrival, and do not teleport through new obstacles. An unreachable task does not hang the simulation.

4.3 · Haul physical goods

Read
Memory replacement and movement APIs; revisit borrowing.
Work
Move a bounded load from storage to another location through a member’s activity. Define the initial carrying capacity.
Done when
Goods remain accounted for across source, transit, and destination. Two members cannot collect the same stock. A blocked destination leaves goods somewhere valid and visible, without duplicating or deleting them.

Checkpoint: watch a terminal scenario deliver food around an obstacle. Reflect: how do ownership in the game and ownership in Rust differ?

5 · Families plan; members act

5.1 · Meet individual needs

Read
Enums and exhaustive matching; member rules.
Work
Add food, rest, and social needs, their changes over time, and actions that satisfy them. Record simple thresholds and consequences.
Done when
Eating consumes actual food, rest takes time at a valid location, and socializing requires another available member. A member with unmet needs can recover when conditions improve.

5.2 · Pursue a family goal

Read
Methods; Iterator API.
Work
Give a family a shared goal to move available supplies into its storage. Let members select and perform work toward it while also satisfying individual needs.
Done when
Members do not duplicate the same work, family goals complete when satisfied, and an urgent need can interrupt activity without losing carried goods or corrupting shared work.

5.3 · Recover from blocked goals

Read
Ordering and comparison; behavioral tests.
Work
Make goal selection and blocked reasons inspectable. Add scenarios with missing food, an unavailable social partner, and unreachable work.
Done when
Blocked work does not prevent unrelated possible activity. Restoring the missing condition allows progress. Repeated selection does not endlessly restart a feasible action.

Checkpoint: a family completes shared work while members eat, rest, and socialize. Reflect: which state is shared, and which member owns the responsibility for progressing an action?

6 · Produce goods and develop skills

6.1 · Produce food and timber

Read
Traits; generics; production rules.
Work
Introduce the two production activities using actual members, workplaces, inputs where applicable, and elapsed work. Decide whether traits or concrete types help this domain; using a trait is not an acceptance requirement.
Done when
Outputs require completed work at the proper place. Interrupted work neither duplicates output nor consumes an input twice. Each production rule identifies its resource sources and sinks.

6.2 · Learn through work

Read
Integer operations; lifetime relationships.
Work
Improve the relevant member skill through completed work and let it affect effectiveness. Define bounds and starting differences between members.
Done when
Relevant work increases the appropriate skill, idle or blocked time does not, and higher skill has a measurable effect. Progression does not overflow or create zero-duration infinite production.

6.3 · Sustain production autonomously

Read
Iteration; family goals.
Work
Let families generate production and hauling work based on their goals and stock. Expose why members choose their current activities.
Done when
A multi-day run produces and consumes resources without player assignment of individual tasks. All members still work for their own families. Different starting skills remain visible in the results.

Checkpoint: observe a working food and timber economy before trade. Reflect: where did traits or generics improve clarity, and where would they add unnecessary abstraction?

7 · Exchange goods and discover prices

7.1 · Complete one trade

Read
Result API; market rules.
Work
Complete a family-to-family trade at the current common price, including payment, delivery, and ownership changes.
Done when
Funds and goods are conserved. Insufficient funds, unavailable stock, changed circumstances during delivery, and repeated completion cannot create a partial or duplicate exchange. Hauling remains physical.

7.2 · Generate demand and supply

Read
Collections; ordering contracts.
Work
Let families request goods they need and offer surplus. Define how competing orders are considered at the common price.
Done when
Competing buyers cannot buy the same goods or overcommit their funds. Unmet demand is visible, satisfied or withdrawn demand disappears, and repeated planning does not multiply one need into many orders.

7.3 · Let the player trade

Read
Representing alternatives; player stock policies.
Work
Add policy commands for the player warehouse: buying/selling enabled flags, buy-up-to quantities, and sell-down-to reserves.
Done when
Player purchases respect treasury funds and target stock; sales respect reserves. Policy changes affect pending demand. The player cannot trade with itself or repeatedly buy and resell its own order.

7.4 · Adjust the common price

Read
Numeric bounds and arithmetic; price behavior.
Work
Choose and document a periodic price adjustment rule based on demand and supply. Apply it to every resource.
Done when
Shortage with unmet demand raises the price, surplus lowers it, and no activity leaves it unchanged. Prices remain within bounds. Every exchange in an interval uses the same resource price, including player trades, and old observations do not accumulate forever.

Checkpoint: cause a shortage, watch the price rise, then restore supply. Reflect: what distinguishes an intention to trade from a committed transfer?

8 · Build autonomously and on public land

8.1 · Validate a construction site

Read
Choosing error behavior; land rules.
Work
Add a building catalog with footprints, access requirements, material costs, work requirements, and intended use. Accept or reject proposed sites.
Done when
Valid multi-tile sites pass; out-of-bounds, wrong-owner, overlapping, and inaccessible sites fail without side effects. Accepted sites cannot overlap each other.

8.2 · Hire and pay builders

Read
Pattern syntax; construction contracts.
Work
Create a construction request, agree a builder-family contract, deliver materials, perform work at the site, and settle the fee.
Done when
A building appears only after required work, materials, and payment. The builder is paid once. Two requests cannot spend the same commitments. Blocked paths, insufficient funds, and absent builders produce visible blocked states; self-construction follows its special payment rule.

8.3 · Let a family choose its building

Read
Collection query APIs; family goals.
Work
Let family goals select a needed building and a valid location, obtain missing materials through trade, and hire builders.
Done when
A family expands without the player selecting the type or location. No-space and unaffordable scenarios stay stable without duplicate contracts. Meeting the need stops further equivalent requests.

8.4 · Designate public buildings

Read
Visibility and boundaries; player actions.
Work
Let the player choose public building types and locations. Fund them from the treasury and public stock, and make their completed functions usable.
Done when
A manually designated warehouse or meeting place is built by a builder family. Its function works without staff, its spending is charged to the player, and the command cannot build on private land.

Checkpoint: observe a private building and designate a public one. Reflect: what remains true when construction is interrupted halfway through?

9 · Settle taxes

9.1 · Collect fee farm

Read
prototype tax rules; source tax definitions.
Work
Let the player configure a zone’s fee farm amount and collect it at the season boundary.
Done when
Full, partial, zero-fund, and zero-tax cases are correct. Shortfalls are forgiven. A boundary collects once, public land is untaxed, and multiple-zone settlement follows a documented order.

9.2 · Pay stewardry and collect output

Read
Matching alternatives; stewardry scope.
Work
Enable stewardry for production zones. Direct entitled output to the player and pay the family its seasonal amount.
Done when
Only output produced under stewardry changes entitlement. Goods are hauled and cannot also be sold by the family. An underfunded treasury pays partially without debt; an unavailable warehouse does not lose output.

9.3 · Change policies across seasons

Read
Integration tests; timing and nonretroactivity.
Work
Exercise tax changes alongside production, trade, and construction over multiple seasons.
Done when
Switching arrangements follows the documented next-boundary payment rule, never seizes old stock, and never settles both arrangements for one zone in the same season. Committed funds cannot be spent twice across taxes and construction.

Checkpoint: run both tax arrangements in one settlement. Reflect: how are tax policy, ownership entitlement, and physical inventory different?

10 · Save and resume the simulation

10.1 · Serialize a complete world

Read
Serde overview; derive support; serde_json.
Work
Define a versioned save representation and round-trip a world with active goals, trades, hauling, construction, skill progress, and market observations.
Done when
Reloaded state continues to the same observable outcome as uninterrupted state under the same subsequent inputs. Saving includes more than the visible buildings and people.

10.2 · Handle files and bad saves

Read
Filesystem APIs; I/O; Error trait.
Work
Add manual save/load commands using a local save slot. Validate loaded domain state and reject unsupported versions.
Done when
Missing files, malformed data, invalid ownership/inventory, and incompatible versions produce useful errors. Failed loads leave the current world unchanged; failed or interrupted writes preserve the previous valid save.

10.3 · Exercise recovery

Read
File operations and persistence guarantees; save rules.
Work
Add scenarios that stop and reload during resource delivery, tax transitions, and construction. Describe the local filesystem guarantees your save procedure relies on.
Done when
Recovery does not reissue payments, duplicate materials, forget demand, or replay a season boundary. The terminal can save, exit, restart, and resume. Server-scheduled autosave is added in module 13.

Checkpoint: resume a busy town after process restart. Reflect: what belongs in durable world state, and what should be reconstructed at runtime?

11 · Give the world a server

Add Tokio and Axum here. Their tutorials include unrelated generic examples; your exercise is the game’s own protocol. Keep the simulation usable without a running network service.

11.1 · Define the browser contract

Read
Cargo workspaces; enum serialization.
Work
Define serializable player commands, command results, and world views. Arrange native and future browser code so they share the contract without requiring native server dependencies in Wasm.
Done when
The contract covers every player action, including inspection, pause/speed, and save/load. Valid messages round-trip, malformed ones fail, and a view exposes enough information for the planned browser controls.

11.2 · Serve one authoritative settlement

Read
Concurrency and Send/Sync; async and futures; Tokio tutorial; Axum API.
Work
Run the world behind a local server. Accept commands and expose state through a persistent browser-compatible connection. Use WebSockets for this course’s initial connection lifecycle.
Done when
Two test clients affect the same world, invalid commands do not corrupt it, and each accepted command takes effect once. The server determines results and update order. Simulated time is independent of message or render frequency.

11.3 · Handle connections and time

Read
Axum WebSockets; Tokio time; synchronization primitives.
Work
Track active clients, stop ticks when none remain, and preserve manual pause/speed state. Handle stalled clients and abrupt connection loss.
Done when
The last disconnect stops time; reconnect does not catch up offline time or override manual pause. A dropped connection is eventually detected without relying on a clean close frame. A slow client cannot block world progress or grow an unbounded outbound backlog.

Checkpoint: drive the town with two test clients. Reflect: what do Send and Sync guarantee, and what ordering guarantees did your application still need to establish?

12 · Build the Rust/Wasm browser

Start with browser APIs through wasm-bindgen and web-sys, a canvas map, and ordinary page controls. Add wasm-pack when beginning this module. Small HTML/CSS and JavaScript loader glue are acceptable; the frontend application logic is Rust. No JavaScript framework or game engine is required.

12.1 · Build and load a browser crate

Read
wasm-bindgen guide; wasm-pack build and web target; Wasm target limits.
Work
Add the browser crate and repeatable packaging/serving commands. Load a visible Rust-produced status in the browser over local HTTP.
Done when
A clean checkout can build and load the frontend, generated files stay out of Git, and browser console failures are visible. Compiling a Wasm file alone is not completion.

12.2 · Draw and inspect the town

Read
Canvas API; Window and animation callbacks; Rust callback lifetimes.
Work
Render a world view as colored tiles and symbols. Allow selection of a tile, building, family, and member to inspect their relevant state.
Done when
Multi-tile footprints, members, zones, and public land are distinguishable. Selection remains correct after resizing. Member goals, needs, skills, carried goods, and blocked reasons are readable without relying on color alone.

12.3 · Connect and submit player actions

Read
Browser WebSocket API; event listeners.
Work
Connect the view to the server. Add invitation, land assignment, public construction, pause/speed, and manual save/load controls.
Done when
Commands change authoritative state and rejected actions show their reason. Browser rendering does not run the simulation. Reconnecting restores a current view without blindly replaying commands already sent.

12.4 · Manage the economy from the browser

Read
Input controls; prototype interaction checklist.
Work
Add tax configuration, player trading policies, market prices, family finances, treasury, stocks, construction progress, and connection status to the interface.
Done when
Every required management action is possible without terminal intervention. Current values and validation errors are visible. Graphics can be replaced without changing the simulation rules.

Checkpoint: manage a local town from one browser. Reflect: how do Rust callback lifetimes differ from JavaScript garbage-collected closures?

13 · Finish the shared local prototype

13.1 · Coordinate two managers

Read
Task communication; shared authority rules.
Work
Open two browsers and exercise conflicting land assignments, construction requests, spending, speed changes, and load operations.
Done when
Both clients converge on one result. Conflicts cannot duplicate land or money. Loading replaces the world for both browsers and rejects commands from the old world. A reconnect cannot duplicate an earlier action.

13.2 · Autosave and shut down cleanly

Read
Tokio shutdown; interval scheduling; autosave requirements.
Work
Add changed-world autosaving on the agreed real-time interval, last disconnect, and graceful shutdown. Keep manual and autosave slots separate.
Done when
Paused edits are saved, disconnect saves do not advance time, and failure preserves the last good file and is reported. Concurrent save/load activity cannot overwrite a newer world with an older in-flight save. Restart and load continue active work correctly.

13.3 · Demonstrate the complete sandbox

Read
Build profiles; elapsed-time measurement; full completion scenario.
Work
Run the full scenario in the rules, record its commands and manual browser steps, and measure tick/render performance on the starter settlement. Update the tooling guide for the finished application.
Done when
Every required feature is demonstrated, tests and checks pass, and the documented local startup works after a clean build. The starter town keeps up at 1× on your machine; record measurements and address measured bottlenecks. Record remaining balance limitations without treating them as correctness failures.

Checkpoint: a playable, resumable town shared by two local browsers. Reflect: which complexity was necessary for the rules, and which could you now remove?

After the prototype

Choose these as separate future modules; they are not hidden requirements for finishing this course:

  • Relationships and marriage, then household membership changes and their ownership consequences.
  • Crime and consequences, with individual goals that can conflict with family goals.
  • Outside employment, wages, and staffed public buildings.
  • Additional professions, production chains, recruitment rules, and economic balancing.
  • Sprites, animation, larger maps, and performance work based on measurements.
  • Advanced Rust topics when justified: custom traits, dynamic dispatch, smart pointers, parallel simulation, macros, or low-level optimization. Unsafe Rust is not a course requirement.

No calendar deadline applies. Completion means you can explain your code and demonstrate the behavior, not that you have used every Rust language feature.
